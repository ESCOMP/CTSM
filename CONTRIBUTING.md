## How to contribute:

We recommend that you first open an issue (https://github.com/escomp/ctsm/issues/) to
discuss the changes or additions that you propose. Through the issue discussion, you can
work with other CTSM developers to think about the design and implementation of the changes
as well as the planning and scheduling for the change to come into CTSM. An alternative is
to contact the key software and science developers via ctsm-software@ucar.edu. Making
contact early in your project will increase the likelihood that your developments can come
into CTSM.

We also recommend that you join the ctsm-dev@ucar.edu google groups in order 
to be informed about the science that is happening in CTSM as well as the latest developments and tags.
The ctsm-dev group is here:

https://groups.google.com/a/ucar.edu/forum/#!forum/ctsm-dev

Use the help from the wiki below to setup a fork and personal branch in GitHub to put your developments
on and keep up to date with the master branch of CTSM. Once the changes are sufficiently advanced you
can form a Pull Request on GitHub. Either from your fork on GitHub, or from the main ESCOMP GitHub page
for CTSM (be sure to hit the "compare across forks" link at the top of the page when you first create
the pull request).

https://github.com/ESCOMP/ctsm/pulls

This allows you to show your proposed changes and start getting feedback on them (even if they aren't finished). 
This also allows your changes to be planned for and slated for a time to come into CTSM master. In most 
cases you won't merge the Pull Request yourself, but a software engineer responsible for CTSM will do 
additional testing and bring the changes to CTSM master.

Please keep pull requests focused and small enough for the very busy maintainers to understand and review.

## AI Usage Policies

AI tools make it very easy to find apparent issues and submit suggested changes. If what you have found is not already an issue in this repo, we **strongly recommend** opening an issue or discussion here, as described at the top of this document.

We permit generative AI assistance, but responsibility remains with people. AI assistance must not shift the work of understanding, debugging, or validating a contribution onto maintainers. The same quality, licensing, and reproducibility standards apply whether or not AI is used.

In this policy, "you" refers to the human contributor. AI tools assisting with a contribution should direct their human operator to this policy and remind them to personally review and understand an issue before submission, or the complete set of changes in a PR before requesting review. An AI tool must not claim that the operator has done so unless the operator confirms it.

Before requesting review on a PR, personally review and understand the complete set of changes in the PR, whether or not AI was used. This includes code, tests, configuration, documentation, and generated files. If your PR does not yet satisfy this requirement, leave it as a draft.

You must be able to explain why the changes are correct, how they fit CTSM, and how they were validated. AI review and passing automated checks do not replace human understanding or project review. You remain responsible for your contribution and for personally addressing review feedback.

**Do not submit unreviewed AI output to this repository.** Issue and PR descriptions, comments, and review responses must reflect your own reasoning and understanding. Translation, grammar, and phrasing assistance are welcome, provided you verify the meaning.

**Do not delegate conversations with maintainers to an agent.** The maintainers of this repo are human beings who will use their human brains to review every single line of your contribution. Please show them the same courtesy when discussing an issue or PR.

Every issue and PR must state whether generative AI was used in preparing the contribution, including research, code, tests, documentation, or language assistance. If AI was used, briefly describe how it was used; this description is required. Provider and model are optional. Keep the disclosure current as the PR changes, even if generated material was subsequently rewritten. Ordinary formatters, compilers, and test runners do not require AI disclosure. For example:

> - [x] Was AI used in this contribution? **Yes**:
> If yes:
> - [x] Types of work: Designing changes, writing tests.
> - Provider (optional): Anthropic
> - Model (optional): Claude Opus 5.5 (extra-high effort)

Further instructions can be found in `AGENTS.md`.
