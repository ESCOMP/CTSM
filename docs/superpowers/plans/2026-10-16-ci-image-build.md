# Build the CI image in CI (NEXT_STEPS item 8) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Step 0 of every task is the orchestrator's own work, never the implementer's, and it always ends with a stop for the user's approval, even when nothing needed changing. See "Every task" under Global Constraints.**

**Goal:** A GitHub Actions workflow builds `ctsm-ci-derecho-gnu` natively for x86_64 on the Cirrus runner and for arm64 on GitHub's arm runner on every labeled PR that touches the recipe; on merges to `master` it validates both images, publishes an attested multi-arch manifest to GHCR, and opens an issue, addressed to the people who caused the publish, saying which tag to pin in `cirrus-testing.yml`.

**Architecture:** One workflow, four jobs, running only in `ESCOMP/CTSM`. `setup` enforces the repository guard and the PR label gate, and computes the tag and the publish flag. `build-amd64` runs on `gha-runner-ctsm`: it builds against a registry-backed layer cache, then runs every x86_64 gate in the same job — the two smoke tests, CTSM's 55 unit tests via `run-unit-tests-in-container.sh`, and a single-point system test via `run-test-in-container.sh` against the runner's read-only inputdata mount — and saves the image as a workflow artifact. `build-arm64` runs on `ubuntu-24.04-arm` (CIRRUS has no arm64 hardware yet): build, smoke tests, artifact. `publish`, only on `master`, loads both artifacts, pushes the per-arch tags, assembles the manifest (`YYYYMMDD-<7sha>`, `latest`), attests all three digests, and opens the repin issue. No QEMU anywhere; nothing is tagged until every gate has passed; the pin in `cirrus-testing.yml` stays a human edit.

**Tech Stack:** GitHub Actions (`gha-runner-ctsm` self-hosted + `ubuntu-24.04-arm` + `ubuntu-latest`), podman (`build --cache-from/--cache-to`, `save`/`load`, `push --digestfile`, `manifest`) — or Docker with Buildx if Task 2 finds that instead (Appendix A) — `actions/upload-artifact`/`download-artifact`, `actions/attest-build-provenance`, `JasonEtco/create-an-issue` (both already pinned in this repo), `gh` and `jq` (preinstalled on hosted runners), bash. No Python.

**Spec:** `docker/ctsm-ci-derecho-gnu/NEXT_STEPS.md` item 8 (lines 666–798 at the time of writing), plus the decisions in this plan's Context section, which win where the two differ. Task 5 writes those decisions back into item 8.

**Location:** `docs/superpowers/plans/2026-10-16-ci-image-build.md`. **Status: draft, not yet approved by the user** (2026-10-16); saved but uncommitted. Branch: `cirrus-runner-workflows`; the CI that exercises it is ESCOMP/CTSM PR #3389 (draft, base `master`), whose `pull_request` runs reach `gha-runner-ctsm`. The fork `samsrabin/CTSM` has **no** self-hosted runner: its `cirrus-testing.yml` jobs have sat queued since 2026-10-15, which is what "the runner is registered on the base repository" looks like.

Confirmed: the run, not `--no-run`; if inputdata symlinks dangle on the runner, Task 6 chooses another test or `--no-run` with the user.

- **The workflow runs only in `ESCOMP/CTSM`.** A guard on `setup` skips everything elsewhere. On a `pull_request` event the repository is the base repository, so a PR from a fork into ESCOMP still gets its build (on ESCOMP's runners, with a read-only token), while pushes to fork branches and PRs within forks do nothing. A fork could never complete a run anyway: it has no Cirrus runner.

The check reads the PR's labels live (not from the event payload), so adding the label and clicking "Re-run failed jobs" is enough; no push needed. Pushes to `master` and `workflow_dispatch` are not gated.
- **The publish run opens an issue, not a PR** (`GITHUB_TOKEN` cannot push a change under `.github/workflows/`, and a PR it opens triggers no `pull_request` workflow). **The issue is addressed to the people responsible for the publish**: whoever merged (or dispatched), plus the authors of the commits that came in. What GitHub exposes for that, and its limits, is in Task 4.
- **Task 1 strictly precedes everything.** Nothing is pushed until both `cirrus-testing.yml` jobs are green.
- **The untracked drift-check plan is not this plan's business.**
- **Every task starts with a review step and ends with a commit followed by a stop for the user's review.**

Calls made in this plan without asking (each reversible; flagged so they can be rejected):

- **podman is the planned tool on every leg, with Docker as the measured alternative.** The Cirrus runner is an ARC Kubernetes pod using the k8s container hook (NEXT_STEPS item 13 names `/home/runner/k8s/index.js`), which is the mode normally chosen when there is no Docker daemon; but the CIRRUS admin's suggestion of `docker/build-push-action` points the other way, so this is a guess until Task 2 measures it. GitHub's hosted Ubuntu images (x86_64 and arm64, image 20261004) ship both: Podman 4.9.3, Buildah 1.33.7, Skopeo 1.13.3, Docker 28.0.4 with Buildx. One tool on every leg is the rule either way. With podman the wrapper scripts run unmodified (`podman` is their default; the image is tagged `localhost/ctsm-ci-derecho-gnu:dev`, their default `IMAGE_TAG`) and the manifest recipe already exists in this repo (`doc/ctsm-docs_container/README.md:51-80`). **If Task 2 finds Docker and not podman on the Cirrus pod, Appendix A applies**: Docker on all three jobs, and the scripts gain a runtime variable because they hardcode `podman`.
- **Layer cache in its own GHCR package**, `ghcr.io/escomp/ctsm/ctsm-ci-derecho-gnu-cache`. podman's `--cache-to` writes one small cache image *per Dockerfile step*, each under its own tag, so it cannot share a package with the image without burying the real tags. The package is created private by the first publish and must be made public once (Task 7) or PR builds from forks cannot read it and run cold. `--cache-to` runs only when publishing (the only time the token can write); `--cache-from` always. Two staleness controls: `--cache-ttl=720h` (30 days) on every build, so a frozen `dnf install` or `wget` layer is refreshed at least monthly, and a `no_cache` `workflow_dispatch` input for an on-demand clean rebuild (the "base-image or upstream-tarball refresh" case item 8 names). Old cache entries are never garbage-collected by GHCR; cleanup is a follow-up, not part of this plan.
- **The x86_64 gates run inside the build job**, sequentially, on the Cirrus runner. Self-hosted jobs have no 6-hour limit, each validation is about 10 minutes on Casper's 16 cores (user's figure; scales with the pod's CPU quota), and it avoids moving a 3 GB image between runner pods just to validate it.
- **Only the `publish` job writes image tags.** Both legs hand their image over as a one-day workflow artifact (`podman save | zstd`); `publish` loads them, pushes the per-arch tags, builds the manifest. The legs' only registry writes are the cache.
- **The image name is hardcoded** to `ghcr.io/escomp/ctsm/ctsm-ci-derecho-gnu`: with the repository guard, deriving it from `github.repository` would always give the same answer, and the literal is clearer. `cirrus-testing.yml` keeps its hardcoded pin.
- **`MAKE_JOBS` comes from the cgroup CPU quota, not `nproc`.** A Kubernetes pod's `nproc` reports the node's cores while the pod is throttled to its quota — the same oversubscription the Dockerfile comment at `:71-76` warns about for PBS.
- **Trigger paths follow the item exactly** (`docker/ctsm-ci-derecho-gnu/**` minus `*.md`, plus the workflow file). A change to `check-derecho-versions.py` therefore also rebuilds (cached, minutes) and re-validates (about half an hour of Cirrus time), and also trips the label gate. Narrowing that is a one-line change if it proves annoying.
- **The disk-reclaim step on hosted runners reports, it does not gate.** The build's peak disk is first measured by Task 6; README records it then.

1. **A fork PR's read-only token.** `podman login` must not fail the job, `--cache-to` must be absent, no push attempted. → Task 6 acceptance: the PR run's amd64 log shows the login step succeeding, the build command without `--cache-to`, and no `publish` job.

The `paths:` filter covers the second half by reading.
3. **A gate fails after the cache was written.** `publish` must not run, so no tag moves. → Task 4 Step 1: `publish` has `needs:` on both legs and the `if:` on the publish flag (default `success()` semantics do the rest); Task 6 does not exercise this path, so the reviewer checks it by reading.
4. **A commit whose author e-mail is not linked to a GitHub account** has no `username` in the push payload; the mentions step must not emit `@null` or abort. → Task 4 Step 3 test `test_publish_mentions.sh`, fixture with a null username and a `web-flow` committer.
5. **The arm64 recipe has never been built**, and the hosted arm runner is the one leg still under the 6-hour, 4-core, ~14 GB constraints. The Dockerfile's only architecture-specific text is a comment (`:775`); GCC is `--disable-multilib`, ESMF autodetects `ESMF_ABI`, AlmaLinux's `crb` repository exists for aarch64. → Task 6 reads the arm64 log; a genuine architecture or capacity failure is a decision for the user (fix, defer arm64, or ship amd64-only), not something the implementer resolves.
